# 实验日志（huashu-flash 爬山循环）

每条：假设 → 最小改动 → 护栏 → 测量 → 去留。

## 实验 1：rebuildCesium（生产构建压缩 + 摇树 Cesium）—— ✅ 保留

- **假设**：默认方案把 6.1 MB 官方预编译 `Cesium.js` 原样拷贝；改为
  `cesium({ rebuildCesium: true })` 从源码打包，经压缩/摇树后 gzip 传输可降
  ~25%，fast4g「能用」p75 相应下降。
- **改动**：`01_Web/vite.config.ts` 一行：`cesium()` → `cesium({ rebuildCesium: true })`。
- **护栏**：`npm run lint` 绿；`npm run build:public` 绿（3451 模块，1.10s）；
  preview 冒烟：地球画布 2400×1576 渲染、NaturalEarthII 瓦片 / Workers /
  SkyBox 贴图全部 200、控制台 0 错误。
- **配对测量**（A=原方案 :4173，B=新方案 :4174，交替 10 轮，fast4g）：
  - A：p50/p75/p95 = 4190/4205/4273 ms，13 请求，2.089 MB
  - B：p50/p75/p95 = 3093/3098/3105 ms，18 请求，1.586 MB
  - **能用 p75 降幅 26.3%**，传输 -24%。
- **代价与取舍**（记录在案）：
  - Cesium 不再是独立稳定文件名 → 部署后应用每次更新，回访用户需重下完整
    JS（~1.36 MB gzip），原方案只需重下 146 KB 应用块。若将来公开部署且重访
    流量大，可再加 `advancedChunks` 把 cesium 拆成独立 chunk（见报告建议项）。
  - 构建时间 384ms → 1.10s（可忽略）。

## 实验 2：/media/user/ 缓存头 —— ✅ 保留

- **假设**：`serveUserMedia` 返回 `cache-control: no-store`，画廊每次访问都
  全量重下全部缩略图；媒体文件按 id 一次性写入、从不原地覆盖，可安全加
  短窗口私有缓存。照片上万后这是画廊翻页/回访的主要传输来源。
- **改动**：`01_Web/scripts/local-editor-plugin.mjs` `serveUserMedia` 一处：
  `no-store` → `private, max-age=86400`（编辑器 API 响应的 no-store 保持不变）。
- **护栏与验证**：lint 绿；dev 重启后 curl 实测
  `cache-control: private, max-age=86400`；删除测试文件后 404 正常。
- **取舍**：彻底删除的照片在缓存窗口内（≤24h）可能仍从浏览器缓存显示。
  本机个人模式可接受；如介意改回 `no-store` 即可。

## 实验 3：requestRenderMode（空闲降帧）—— ❌ 不做（降级为建议项）

- **假设**：Viewer 未开 `requestRenderMode`，空闲时持续 60fps 渲染，开启后
  空闲 CPU/GPU 大降。
- **为何不做**：月球自转、流星雨、星空等动画由 `scene.preRender` 监听驱动，
  开启按需渲染会冻结这些动画，需在所有动画路径补 `scene.requestRender()`
  ——侵入多个组件、与每周自动合并上游的流程冲突风险高，且属用户可感知
  行为（动画卡住=红线）。按 skill「方向」原则记为上游建议项，不在 fork 做。

## 实验 4：cesium 独立 chunk（部署缓存友好）—— ❌ 暂不做

仅影响"公开部署 + 高回访"场景；用户当前为本地 dev 使用，收益为零，
vite.config 增加 ~10 行冲突面。若部署再启用（报告附做法）。
